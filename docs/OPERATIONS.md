# Operations Manual (English)

> Applies to `cultural-tourism-wiki` **v0.1.0**.
> Chinese overview: [`README.md`](../README.md) ｜ English overview: [`README_EN.md`](../README_EN.md)

This manual is the day-to-day operating procedure: how to install the skill, how to run an ingest, how to keep the wiki healthy, and what to do when something breaks. Read it once end-to-end before your first bulk import.

---

## 1. What the skill does

It turns scattered cultural-heritage material (old photos, guide maps, document scans, oral history, PDFs, web pages) into a **Markdown wiki that keeps growing**, and writes **three lenses** — Child / History / Expert — for every entry.

The method comes from Andrej Karpathy's [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f#llm-wiki):

> Knowledge is compiled once and then kept up to date, rather than being re-derived on every query.
> Obsidian is the IDE, the LLM is the programmer, the wiki is the codebase.

Plain RAG re-assembles an answer from raw documents every single time. An LLM Wiki instead has the model **incrementally maintain one persistent structured knowledge base**, where cross-references, contradictions and syntheses are resolved ahead of time — so every new source makes the whole thing thicker instead of starting from scratch.

### Three layers — never mix them up

| Layer | Location | Written by | Read by | Rule |
|---|---|---|---|---|
| Raw sources | `wiki/raw/` | user / skill (write-once) | LLM | **Read-only.** Never edit, rename or delete. This is the evidence trail. |
| Knowledge base | `wiki/pages/`, `index.md`, `log.md` | **LLM, full authority** | user / Dify retrieval | May be added to or rewritten, but every change must leave a trace in `log.md`. |
| Conventions | this skill + `wiki/_config.md` | evolve together | LLM | Project-specific rules go in `_config.md`, **not** into the skill. |

### Layout

```
wiki/
├── _config.md        # project name, persona, lens set, categories
├── index.md          # index (regenerated by script)
├── log.md            # append-only timeline
├── overview.md       # optional guided tour
├── raw/
│   ├── images/       # YYYYMMDD-HHMMSS-description.jpg
│   ├── texts/        # pasted or OCR'd text
│   └── files/        # PDFs, saved web pages
├── pages/
│   ├── entities/  events/  buildings/  people/  topics/
└── lint-report.md    # generated by lint
```

Lenses live **inside** each page under `## 多视角解读` / `## Lenses`. They are not split into separate files on purpose: when Dify chunks the page for retrieval, facts and their three renderings stay in the same chunk.

## 2. Install

### 2.1 As a WorkBuddy / Claude-style skill

```bash
git clone https://github.com/2697772879-cloud/cultural-tourism-wiki.git
cp -r cultural-tourism-wiki ~/.workbuddy/skills/cultural-tourism-wiki
```

The folder name must stay `cultural-tourism-wiki`; the trigger sentence lives in `SKILL.md` frontmatter.

### 2.2 As a Dify Agent skill

Dify follows the Anthropic Skills convention: **`SKILL.md` must sit at the root of the zip.**

```bash
cd cultural-tourism-wiki
zip -r cultural-tourism-wiki-skill.zip SKILL.md references/ assets/ scripts/ docs/
```

Upload at Dify → Agent app → Skills → Upload (< 50 MB), then add a trigger line to the agent's system prompt:

> When the user uploads cultural-heritage material (image / text / PDF / link) or asks to organise the knowledge base or generate multi-lens interpretations, use the "文旅知识库摄取与多视角生成" skill.

**Progressive disclosure:** `SKILL.md` stays short on purpose. If you notice Dify never reads the sub-files, add at the top of `SKILL.md`: “Before running an ingest, read `references/ingest-workflow.md` and `references/schema.md`.”

### 2.3 Requirements

- Python 3.8+ (scripts use the standard library only — no `pip install` anywhere).
- A model with vision capability if you want photo/OCR ingestion.
- Write access to the folder holding `wiki/`.

## 3. Initialize a wiki

```bash
python scripts/wiki_init.py --root wiki \
    --project "Sihao Hotel" \
    --persona "Sihao Hotel resident history guide" \
    --lenses 儿童 历史 专家
```

| Flag | Default | Meaning |
|---|---|---|
| `--root` | `wiki` | wiki root; use `/home/sandbox/wiki` inside Dify sandbox |
| `--project` | `文旅知识库` | project name, appears in index and lens wording |
| `--persona` | `专属文史导游` | first-person persona used in History / Expert lenses |
| `--lenses` | `儿童 历史 专家` | which lenses every page must carry |

The script is **non-destructive**: existing directories and files are reported as “already present” and skipped. After it runs, confirm with the user: project name, lens set, and whether the five default categories fit — then record any project-specific convention in `wiki/_config.md` under “本项目特殊约定”.

## 4. Ingest one source — the seven steps

One ingest = **one source** (a source may contain several images).

Before you start, read `wiki/index.md` in full and hold every existing title + alias in mind. That single habit prevents most duplicate pages.

### Step 1 — Drop it into `raw/`

| Type | Destination | Name |
|---|---|---|
| Image | `raw/images/` | `YYYYMMDD-HHMMSS-short-description.jpg` |
| Pasted text | `raw/texts/` | `YYYYMMDD-HHMMSS-short-title.md` |
| PDF / web page | `raw/files/` | `YYYYMMDD-HHMMSS-title.pdf` \| `.html` |
| OCR output | `raw/texts/` | `YYYYMMDD-HHMMSS-<original>-ocr.md` |

Chinese names are fine; no spaces and none of `\ / : * ? " < > |`; spaces become `-`; keep descriptions under ~20 characters. Keep the original filename on the first line of the text so it can be traced back.

### Step 2 — Extract

**Images** — run OCR / the vision model for text (signboards, inscriptions, captions, handwritten notes). For building photos also record: structural type (arcade / clock tower / watchtower / courtyard), materials (grey brick / red brick / terrazzo render / timber), components (arches, columns, carved staircase, Manchurian windows, plaster relief), and condition (repair traces, weathering, later additions). For old photos also note camera angle, any legible signage, clothing, street-context — these are usually what dates the image.

Unreadable characters become `□`; an uncertain passage gets `[需人工复核]`.

**Text** — clean (strip headers/footers, normalise full/half width, repair broken lines), split into段落, then produce:

```markdown
### Source summary
- Core topic:
- Time:
- Place:
- People:
- Events:
- Candidate pages: [building] Clock Tower / [person] Guo Siquan / [topic] Repair techniques
- Doubts:
```

### Step 3 — Write the fact base first

Every page has a `## 事实底座` (fact base) section. Each bullet carries a provenance anchor:

```markdown
- The four-faced clock was installed on the top storey <!-- src: raw/images/20260917-103000-sihao-clock-tower.jpg -->
- Reopened in May 1948 <!-- src: raw/texts/20260917-104500-sihao-history.md --> `[需人工复核]`
```

Anchors are HTML comments: invisible when rendered, greppable by the lint script. Anything the model **inferred** rather than read goes into a separate list marked `[推断]` — never inline among the facts.

### Step 4 — Create or merge

```
Look up index.md + every page title/alias
│
├─ Same name or alias exists?
│   ├─ yes → same referent? → yes → MERGE (default)
│   │                       └─ no  → create new page + add a “not to be confused with”
│   │                                note on both pages + bidirectional links
│   └─ no → semantically close entry exists (a component of the same building,
│           the same event in a different year)?
│            ├─ yes → small amount of info? merge into the parent page as a subsection
│            │        enough to stand alone? create a child page + link both ways
│            └─ no  → create new
```

**Merging is not appending.** On a merge you must:

1. fold new facts into the fact base with their new `src` anchors;
2. **revise** the summary — the old one is often no longer accurate;
3. de-duplicate the body; where two wordings state the same fact, keep the more precise one;
4. append to `sources`, bump `updated`, add a line to `## 修订记录`;
5. **regenerate all three lenses** — if the fact base changed, the lenses must change;
6. on contradiction, keep **both** readings with their own sources, never adjudicate. Add at the top of the page:

```markdown
> ⚠️ 冲突：本页存在互相矛盾的说法，见「事实底座」第 2、5 条。[需人工复核]
```

### Step 5 — Generate the lenses

Order is fixed: Child → History → Expert. Each lens is self-contained (readable alone) and must not contain any fact absent from the fact base. See `references/lenses.md` for tone, length and the required opening lines.

| Lens | Length | Must contain |
|---|---|---|
| Child | 150–300 chars, ≤ 3 points | no jargon; a metaphor for every technical term |
| History | 400–800 chars | a clear timeline or causal chain; say “one account says… another says…” when uncertain |
| Expert | 500–1000 chars | a **boundary / limitation** paragraph — what is proven, what is推测, what material is still missing |

### Step 6 — Index and log

- `index.md`: **regenerate with the script.** Hand-written indexes always drift.
- `log.md`: append by hand, one entry per ingest, using the fixed prefix:

```markdown
## [2026-09-17 10:30] ingest | sihao-clock-tower.jpg
- 落盘：raw/images/20260917-103000-sihao-clock-tower.jpg（图片，用户上传）
- 新建：pages/buildings/钟楼.md
- 更新：pages/entities/思豪大酒店.md、pages/topics/骑楼.md
- 视角：3（儿童 / 历史 / 专家）
- 复核：signboard year OCR uncertain [需人工复核]
```

Because every entry starts with `## [`, you can always run `grep "^## \[" log.md | tail -5`.

### Step 7 — Report

Always finish with a short report: sources ingested · pages created · pages updated · lenses generated · items needing human review · next step.

**One source should normally move 5–15 pages.** Before you stop, check: main page · every mentioned existing entity/person/building (add a cross-reference or fact) · related topic pages · timeline event pages · backlinks from newly created pages · `index.md` · `log.md`. If you only created one page, you are not done.

## 5. Other commands

| Intent | Command | Behaviour |
|---|---|---|
| Init | `/wiki init` | create skeleton + `_config.md` |
| Ingest | `/wiki ingest` | steps 1–7 above |
| Rewrite a lens | `/wiki lens <page>` | read the fact base, replace **only** that `### XX视角` section, bump `updated`, log it |
| Query | `/wiki query <question>` | read `index.md` first, drill into pages; a good answer may be saved back as a new page |
| Lint | `/wiki lint` | see §7 |

Natural language is accepted — “archive this photo”, “write a kids version for the clock tower”, “check the knowledge base”. Route by intent; do not ask the user to pick a command.

## 6. Scripts

All three are pure standard library and run unchanged on Windows, Linux and the Dify sandbox.

```bash
python scripts/wiki_init.py  --root wiki --project "Sihao Hotel"
python scripts/wiki_index.py --root wiki [--dry-run]
python scripts/wiki_lint.py  --root wiki --out wiki/lint-report.md [--stale-days 30]
```

| Script | Output | Notes |
|---|---|---|
| `wiki_init.py` | directories + `index.md` + `log.md` + `_config.md` | skips whatever already exists |
| `wiki_index.py` | rewrites `index.md` | groups by category, sorts by title, adds a stats table; `--dry-run` prints only |
| `wiki_lint.py` | prints a report, optionally writes `--out` | 9 structural checks, see below |

### What lint checks

frontmatter completeness · missing lens sections · broken `[[links]]` · orphan pages (no inbound link) · missing `src` anchors · suspected duplicates (title similarity ≥ 0.85) · index drift · raw files no page references · `draft` pages older than `--stale-days` · a `[需人工复核]` review queue.

Lint covers structure only. **Semantic checks are the model's job** and are listed in `references/lint.md`: cross-page contradictions, stale summaries, lenses that wander outside the fact base, missing pages for repeatedly mentioned concepts, over-confident low-confidence pages, knowledge gaps.

## 7. Batch ingestion

1. **List first** — drop every file into `raw/` and log them. Do not generate yet.
2. **Light triage** — produce only the source summary + suggested category for each, and show the user.
3. **Then go deep** — after confirmation, generate full pages and lenses one by one.
4. **Batch size 5–10**, running `wiki_lint.py` between batches.
5. **Shorten lenses** in bulk mode (Child 100 / History 300 / Expert 400 chars) and refine the key entries individually later.

### Idempotency

Before dropping a file, hash its contents and compare against `raw/.manifest.tsv` (path · hash · ingest time). On a hit, reply “this was ingested at X, it touched these pages — reprocess?” and create nothing.

## 8. Page schema (quick reference)

```yaml
---
title: Clock Tower
type: building            # entity | event | building | person | topic
tags: [clock-tower, grey-brick, arcade]
status: draft             # draft | reviewed
confidence: medium        # high | medium | low
aliases: [Sihao clock tower]
sources:
  - raw/images/20260917-103000-sihao-clock-tower.jpg
created: 2026-09-17
updated: 2026-09-17
---
```

Required: `title` `type` `tags` `status` `confidence` `sources` `created` `updated`.
Optional: `aliases` `location` `period` `related`.

Categories: `entity` (named institution/object/place — Xiangshan Bank, Fengshui Well), `event` (a dated occurrence — 1948 reopening), `building` (a structure or component — clock tower, arcade façade), `person` (a named individual), `topic` (a technique, system or price regime — repair techniques, room pricing). If it could be `building`/`person`/`event`, do not put it in `entity`. If `entity` vs `topic` is unclear: “a thing” → entity, “a way of doing something” → topic.

`status` and `confidence` exist so Dify retrieval can down-rank or flag shaky pages; a `low` confidence page should read cautiously.

## 9. Images

- Page syntax `![description](URL)`. Prefer Dify's built-in file service URL, then object storage.
- Under 2 MB per image (Dify limit), JPG/PNG. Compress first: long edge ≤ 1600 px, 100–350 KB.
- The original **always** stays in `raw/images/`, even when the page renders a compressed copy.
- Write the caption as a description of what is in the frame, not the filename.
- Keep both the relative `raw/` path (local traceability) and the HTTP URL (online rendering) on the page. Dify only resolves the latter.
- Enable a **multimodal embedding model** on the Dify knowledge base if you want image search.

## 10. Dify notes

- **Path**: use `/home/sandbox/wiki/` inside the sandbox; never hard-code an absolute path in the skill — read it from `_config.md` or the user's instruction.
- **Persistence**: the sandbox may be rebuilt and lose data. Tar `wiki/` into Dify file storage after each ingest, or keep it under Git (recommended: diffs and rollback).
- **Chunking**: upload `wiki/pages/*.md` **one page per chunk**. Retrieval then hits exactly one entry, and the three lenses are never split apart.
- **Division of labour**: the skill *produces*, the Chatflow *consumes*. Good answers produced in the Chatflow should be saved back as new wiki pages — that is the compounding part of an LLM Wiki.
- **Cost**: two-stage (cheap model for summary + suggestion, strong model for pages and lenses); shorten lenses in bulk mode; compress images; enable caching and conversation summarisation; set a token quota; sample-check OCR and dates instead of full review; audit monthly.

## 11. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `错误：目录不存在 wiki` | wiki not initialised | run `wiki_init.py --root wiki` first |
| Pages missing from `index.md` | index edited by hand or not regenerated | `python scripts/wiki_index.py --root wiki` |
| Many broken links | naming drift (spaces, synonyms) | consolidate names; add `aliases`; fix the links lint reports |
| Lint reports “no source anchor” | facts written without `<!-- src: ... -->` | re-read the source, add anchors; delete or mark `[推断]` what cannot be sourced |
| “raw file not referenced” | archived but never ingested | ingest it, or log why it is not part of the wiki |
| Same fact differs across pages | genuine contradiction | keep both, add `⚠️ 冲突` on both pages, log `[需人工复核]` — do not pick a winner |
| Iframes/images not rendering in Dify | only a relative path on the page, or file > 2 MB | add the HTTP URL; compress under 2 MB |
| Duplicate pages keep appearing | index not read before ingest | always read `index.md` + aliases before step 4; run lint after every batch |
| Chinese output garbled on Windows console | console code page | scripts already reconfigure stdout to UTF-8; if piping, use `PYTHONIOENCODING=utf-8` |

## 12. Conventions checklist (pin this next to your desk)

1. **No fabrication.** Every fact must resolve to something in `raw/`. No source → do not write it, or put it under “待补充” with `[需人工复核]`.
2. **Keep the details.** Dates, addresses, personal names, building components, dimensions, prices — copy them verbatim, never summarise them away.
3. **Facts first, lenses second.** One fact base, three renderings.
4. **`raw/` is read-only.** Never edit, rename or delete.
5. **Incremental by default.** One source moves 5–15 pages.
6. **Flag what is shaky.** OCR output, dates, names and numbers always get `[需人工复核]`.
7. **Idempotent.** Re-submitting a source merges instead of duplicating.
8. **Scripts own the index.** Never hand-write `index.md`.
9. **Logs are append-only.** Never rewrite history in `log.md`.
10. **Project rules live in `_config.md`.** Do not fork the skill per project.
